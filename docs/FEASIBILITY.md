## Пакетный режим: команды и время

| Команда | Код возврата | Время | Лог `/Out` |
|---|---|---|---|
| `CREATEINFOBASE File="…"` | 0 | 0,6–10 с (первый запуск дольше) | «Создание информационной базы (…) успешно завершено» |
| `DESIGNER /F … /DumpConfigToFiles <dir>` | 0 | около 0,8 с | пусто |
| `DESIGNER /F … /LoadConfigFromFiles <dir>` | 0 / 1 | около 1 с | пусто или список ошибок |
| `DESIGNER /F … /CheckModules -ThinClient -Server` | 0 / 101 | около 0,7 с | «Синтаксических ошибок не обнаружено!» или ошибки |
| `DESIGNER /F … /UpdateDBCfg` | 0 / 1 | около 0,8 с | «Обновление конфигурации успешно завершено» |
| `DESIGNER /F … /DumpCfg <file.cf>` | 0 | около 0,7 с | «Сохранение конфигурации успешно завершено» |
| `ENTERPRISE /F … /C "ForgeSelfTest;<json>"` | 0 | около 2,8 с | самотест пишет результат в JSON |

Общие ключи: `/DisableStartupDialogs /DisableStartupMessages /Out"<лог>"`. Лог пишется в UTF-8 с BOM.
Командную строку нужно собирать вручную: 1cv8.exe разбирает её сам и не понимает экранирование `\"`, которое вставляет `subprocess.list2cmdline`.

## Поведение при ошибках (для парсера логов)

| Ситуация | Загрузка | Проверка модулей | Обновление БД | Текст в логе |
|---|---|---|---|---|
| Синтаксическая ошибка в BSL | **0** | **101** | **0 (!)** | `{МодульУправляемогоПриложения(2,9)}: Ошибка в выражении` + строка с `<<?>>` |
| Зарезервированное слово как имя процедуры (`Выполнить`) | 0 | 101 | — | `{ОбщийМодуль.X.Модуль(1,11)}: Ожидается имя процедуры` |
| Нет `InternalInfo` у объекта | **1** | — | — | `Файл - <путь>, узел - Catalog: Отсутствует внутренняя информация (узел InternalInfo)…` |
| Повтор имени объекта | 1 | — | — | `Справочник.X - Дублирование имени объекта метаданных` |
| База занята сеансом | 0 | 0 | **1** | `Ошибка исключительной блокировки информационной базы. Активны сеансы: компьютер: …, сеанс: 1, …` |
| Право, неприменимое к объекту | 0 | — | — | **ничего**: право молча выбрасывается |

Выводы для `platform1c`:
1. Загрузка с кодом 0 не гарантирует рабочие модули. **Обновление БД тоже проходит с битым модулем**, поэтому пропускать дальше только конфигурацию с чистой проверкой модулей должен наш код.
2. Ошибка загрузки атомарна: конфигурация в базе остаётся прежней.
3. Формат ошибок BSL: `{<Модуль>(<строка>,<колонка>)}: <сообщение>`, следом строка кода с маркером `<<?>>` и режимом проверки. Одна проверка может выдать несколько ошибок, причём одна синтаксическая ошибка может вызвать каскад последующих.
4. Перечни прав по типам объектов берём только из эталона: неверное право не даёт ошибки, а просто пропадает.

## Формат выгрузки (версия 2.21)

- `ConfigDumpInfo.xml`: `format="Hierarchical" version="2.21"`; `Configuration.xml`: `CompatibilityMode=Version8_5_1`, `InterfaceCompatibilityMode=Taxi`.
- Кодировка UTF-8 **с BOM**, переводы строк **CRLF**, отступы табами, в конце файла нет перевода строки.
- Раскладка каталогов: `Catalogs/<Имя>.xml`, `Documents/<Имя>.xml` + `Documents/<Имя>/Ext/ObjectModule.bsl`, `Reports/<Имя>/Templates/<Макет>.xml` + `…/<Макет>/Ext/Template.xml` (СКД), `Roles/<Имя>/Ext/Rights.xml`, `CommonModules/<Имя>/Ext/Module.bsl`, `Ext/ManagedApplicationModule.bsl`.
- **Минимальный XML принимается**, если есть `InternalInfo` с `GeneratedType` (`TypeId`/`ValueId`). Остальные свойства платформа заполняет значениями по умолчанию, **переданные UUID сохраняет**. На этом строятся детерминированные UUID (uuid5).
- Состав `GeneratedType` по типам объектов (категории):
  - Справочник: `Object`, `Ref`, `Selection`, `List`, `Manager`.
  - Документ: те же пять.
  - Табличная часть: `TabularSection`, `TabularSectionRow`.
  - Перечисление: `Ref`, `Manager`, `List`.
  - Константа: `Manager`, `ValueManager`, `ValueKey`.
  - Регистр сведений: `Record`, `Manager`, `Selection`, `List`, `RecordSet`, `RecordKey`, `RecordManager`.
  - Регистр накопления: `Record`, `Manager`, `Selection`, `List`, `RecordSet`, `RecordKey`.
  - Отчёт: `Object`, `Manager`.
  - Подсистеме, роли и общему модулю `InternalInfo` не нужен.
- Платформа сама упорядочивает `ChildObjects` в `Configuration.xml` в каноническом порядке:
  `Language, Subsystem, Role, CommonModule, Constant, Catalog, Document, Enum, Report, InformationRegister, AccumulationRegister`.
- **Круговой обмен стабилен.** Загрузка эталона в чистую базу и повторная выгрузка дают побайтно те же файлы, кроме `ConfigDumpInfo.xml`: в нём хеши `configVersion` меняются при каждой загрузке. Генератор этот файл **не создаёт**, для полной загрузки он не нужен (проверено).

### Эталон

`reference/2.21/warehouse/` — каноническая выгрузка конфигурации «ЭталонСклад», собранной из минимального XML (`scripts/recon/build_reference.py`). Состав:

- подсистема `Склад`;
- роль `ПолныеПрава` (роль по умолчанию);
- общий модуль `ФоржСамотест` (серверный, вызов с клиента);
- константа `НазваниеОрганизации` — Строка(100);
- перечисление `ЕдиницыИзмерения`: Штука, Килограмм;
- справочник `Номенклатура`: иерархический (группы и элементы), реквизиты, обязательный реквизит-ссылка на перечисление, табличная часть `Штрихкоды`;
- справочник `Склады`: реквизиты Строка и Булево;
- документ `ПоступлениеТоваров`: нумерация, проведение, движения по `ОстаткиТоваров` (приход);
- документ `РасходТоваров`: движения по `ОстаткиТоваров` (расход) и `ПродажиОбороты`, реквизит Дата;
- регистр сведений `ЦеныНоменклатуры`: периодичность день, независимый;
- регистр накопления `ОстаткиТоваров`: остатки;
- регистр накопления `ПродажиОбороты`: обороты;
- отчёт `ОстаткиТоваров` на СКД: запрос к виртуальной таблице `Остатки`, итоги, вариант настроек;
- модуль управляемого приложения с перехватом `/C ForgeSelfTest;…`.

Этот эталон — источник шаблонов Jinja2 на Этапе 1.

## Проверка без COM: самотест в режиме Предприятия

`ENTERPRISE /F <база> /C "ForgeSelfTest;<путь к json>"`. Порядок работы:
1. `ПриНачалеРаботыСистемы` видит префикс в `ПараметрЗапуска`.
2. Вызывается серверный модуль `ФоржСамотест.ЗапуститьСамотест`, который:
   - создаёт данные: группу и элемент справочника с табличной частью, константу, запись регистра сведений;
   - проводит поступление (10 шт.) и расход (3 шт.);
   - читает `ОстаткиТоваров.Остатки`;
   - выполняет отчёт через `КомпоновщикМакетаКомпоновкиДанных` → `ПроцессорВыводаРезультатаКомпоновкиДанныхВКоллекциюЗначений`;
   - пишет JSON.
3. `ЗавершитьРаботуСистемы(Ложь)`.

Фактический результат: `{"ok": true, "balance": 7, "report_rows": 2, "report_quantity": 7, …}` за 2,8 с. Это и есть проверка критерия «документы проводятся, двигают регистр, отчёт показывает остатки».

## Обнаружение занятой базы

- Эксклюзивное открытие `1Cv8.1CD` (`CreateFile` с `dwShareMode=0`): при открытом сеансе — `WinError 32`, после закрытия файл снова свободен.
- Процессы `1cv8*.exe`, у которых в `CommandLine` есть `/F "<путь к базе>"` (через `Win32_Process`).

Используем оба признака. При занятой базе останавливаемся до `/UpdateDBCfg` и выдаём понятное сообщение; зависшие процессы нашего же пайплайна завершаем по таймауту.

## Модель (подробно — `docs/MODEL.md`)

- Зрение и structured output (`format` = JSON-схема) работают у Gemma 4.
- **Найден баг Ollama 0.34.1–0.34.2:** gemma4:12b частично не помещается в 8 ГБ VRAM и делится между CPU и GPU. В таком режиме при включённом flash attention **генерация по JSON-схеме падает** на 400–550-м токене: `CUDA error: an illegal memory access`, llama-server завершается. Воспроизводится стабильно. Без схемы, на CPU или **с `OLLAMA_FLASH_ATTENTION=0`** всё работает. Модели e4b (целиком в VRAM) и 26b-a4b (MoE) не падают и с flash attention, поэтому по умолчанию выбрана 26b-a4b.
- Приложение Ollama по умолчанию задаёт контекст 131072 (`OLLAMA_CONTEXT_LENGTH`). Наш клиент всегда явно передаёт `num_ctx`.
