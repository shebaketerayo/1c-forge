# Выбор модели

Дата замеров: 2026-09-23, Ollama 0.34.2, RTX 4060 8 ГБ + 32 ГБ RAM + i5-14600KF.
Скрипты: `scripts/recon/model_check.py` (3 теста), `scripts/recon/spec_probe.py`. Сырые результаты: `D:\1CForge\recon\model_results.json`.

## Рекомендация

| Роль | Модель по умолчанию | Почему |
|---|---|---|
| Код и спецификация (`code_model`) | **`gemma4:26b-a4b-it-qat`** | На этой машине генерирует быстрее 12b (37–40 т/с против 18) и точнее построила спецификацию. Не страдает от бага flash attention |
| Зрение (`vision_model`) | **`gemma4:26b-a4b-it-qat`** (та же) | Одна модель — одна загрузка в память. Раздельные модели поддерживаются конфигом |
| Запасной вариант (RAM < 24 ГБ) | `gemma4:12b-it-qat` | Лучше всех разобрала эскиз, но требует `OLLAMA_FLASH_ATTENTION=0` (см. ниже) |
| Слабые машины | `gemma4:e4b-it-qat` | Целиком помещается в 8 ГБ VRAM, 60+ т/с, но качество заметно ниже |

Это расходится с ориентиром ТЗ «12B по умолчанию». Причина: 26B — MoE-модель, на каждый токен активны только около 4B параметров. Поэтому при выгрузке 2/3 весов в RAM она всё равно генерирует вдвое быстрее плотной 12B, которая тоже не помещается в 8 ГБ полностью.
Окончательно выбор подтверждаем на Этапе 2 прогоном 10 эталонных запросов (процент успешных генераций), а не по трём тестам Этапа 0.

Выбор по железу (профили в конфиге):
- VRAM ≥ 20 ГБ → `gemma4:31b-it-qat` или 26b целиком в GPU;
- VRAM < 20 ГБ и RAM ≥ 24 ГБ → **26b-a4b** (текущая машина);
- RAM < 24 ГБ → 12b;
- VRAM < 6 ГБ и RAM < 16 ГБ → e4b.

Общие слабости всех моделей: не сделали табличную часть «Товары» (в тестовой схеме она была необязательной), путают поля числовых квалификаторов, в поле «разделы» пишут описания вместо названий.
Что с этим делаем:
- жёсткая схема DSL (обязательные поля, перечисления вместо свободного текста);
- few-shot примеры и RAG;
- двухшаговое планирование;
- детерминированный автофикс в `spec/`.

Structured output работает у всех трёх моделей: 100% ответов прошли валидацию pydantic.

## Баг: flash attention + JSON-схема + частичная выгрузка

- **Симптом.** `gemma4:12b-it-qat` частично выгружена в RAM (около 30%). Генерация с `format` на 400–550-м токене падает: `CUDA error: an illegal memory access was encountered` (ggml-cuda.cu), llama-server завершается с кодом 0xc0000409, клиент получает HTTP 500. Воспроизводится стабильно на 0.34.1 и 0.34.2.
- **Не воспроизводится:**
  - без `format` (900 токенов текста — OK);
  - только на CPU (`num_gpu=0`);
  - с `OLLAMA_FLASH_ATTENTION=0`;
  - у e4b (целиком в GPU) и у 26b-a4b (MoE), даже с flash attention.
- **Позже баг проявился и у 26b-a4b**: на шаге анализа с длинным промптом (RAG-контекст) она упала так же.
  Значит, дело в сочетании частичной выгрузки в RAM, flash attention и JSON-схемы, а не в конкретной модели.
- **Что сделано:**
  - с согласия пользователя задана переменная `OLLAMA_FLASH_ATTENTION=0` (уровень пользователя), Ollama перезапущена;
    в `server.log` теперь `OLLAMA_FLASH_ATTENTION:false`;
  - клиент на всякий случай распознаёт ответ `CUDA error` (HTTP 500) и повторяет запрос на CPU (`num_gpu=0`);
  - пустой ответ без обработанных токенов (бывает сразу после смены моделей в памяти) клиент повторяет сразу.
- **Эффект от выключения flash attention на 26b-a4b** (тот же запрос «учёт склада» с RAG):
  анализ 92 → 26 с, спецификация 136 → 54 с, падений больше не было.

## Настройки Ollama на этой машине

- Модели хранятся в `D:\Ollama\models`: настройка `models` в `%LOCALAPPDATA%\Ollama\db.sqlite` и переменная пользователя `OLLAMA_MODELS`.
- Приложение Ollama задаёт `OLLAMA_CONTEXT_LENGTH=131072`. Наш клиент **всегда** передаёт `num_ctx` явно (по умолчанию 16384), иначе модель выделит огромный KV-кэш и уйдёт в RAM.
- `think=False` для structured output: рассуждения модели в JSON не нужны и только тратят токены. Для шага «анализ предметной области» можно включить.
